# Quint による AI 編集結果の適用仕様

チャットで依頼した AI 編集をいつ反映できるかを、有限状態のモデルで検査する。応答の到着と GUI による取り込みを別々のイベントにして、処理中や応答到着後に起きるキャンセル・字幕編集・素材区間入力の変更を扱う。キャンセル、依頼の無効化、入力の不一致、失敗によって応答を破棄する場合、字幕・適用済みの AI 編集・AI の履歴記録が変わらないことを確認する。有効な応答が編集と履歴を一緒に反映することもシナリオで確認する。 [チャット編集の BDD](../../docs/features/chat-editing.feature) · [作業履歴の BDD](../../docs/features/edit-history.feature) · [Quint モデル](ChatEdit.qnt)

## 開発時の使い方

1. 結果の適用条件を変えるときは、利用者に見える挙動を `.feature` に書く。
2. モデルの遷移と守るべき条件を更新し、イベント順によって仕様が矛盾しないか確認する。
3. モデルで見つけた重要な順序は Rust テストでも確認する。モデルと Rust の対応は変更時にレビューする。 [依頼の状態管理とテスト](../../rust/src/chat.rs) · [GUI 側の入力照合と適用](../../rust/src/main.rs)

モデルは現行の単一クリップ選択を対象とする。一度に処理する依頼は一件で、キャンセル後も応答を取り込むまで処理枠を保持する。字幕と区間入力は二つの代表値に縮め、履歴は AI 編集による記録の有無で表す。TLC の探索対象はこのモデルの到達状態。

## 実行

Node.js、npm、Java を用意する。Quint と npm の依存関係はロックファイルで固定する。初回は依存関係と TLC の取得にネットワーク接続を使う。

```sh
cd verification/quint
npm ci --ignore-scripts
npm run check
```

CI も同じ手順でモデルのシナリオテストと TLC による全探索を実行する。 [Quint の CI](../../.github/workflows/formal-quint.yml)
