# Quint によるエディターの仕様検証

## AI 編集結果の適用

チャットで依頼した単一クリップ編集をいつ反映できるかを検査する。応答の到着と GUI による取り込みを別のイベントとし、その前後のキャンセル、字幕や区間入力の変更、素材や文字起こしの差し替え、手動のクリップ追加を扱う。応答を破棄する場合や素材全体を選んだ場合は編集と履歴を保持し、区間が変わる有効な応答はクリップと履歴に反映する。 [切り出しの失敗・中断・前提変更の BDD](../../docs/features/ai-clip-editing.feature#L81) · [チャット編集の BDD](../../docs/features/chat-editing.feature) · [作業履歴の BDD](../../docs/features/edit-history.feature) · [Quint モデル](ChatEdit.qnt)

## 開発時の使い方

1. 結果の適用条件を変えるときは、利用者に見える挙動を `.feature` に書く。
2. モデルの遷移と守るべき条件を更新し、イベント順によって仕様が矛盾しないか確認する。
3. モデルで見つけた重要な順序は Rust テストでも確認する。モデルと Rust の対応は変更時にレビューする。 [依頼の状態管理とテスト](../../rust/src/chat.rs) · [GUI 側の入力照合と適用](../../rust/src/main.rs)

モデルは現行の単一クリップ選択を対象とする。一度に処理する依頼は一件で、キャンセル後も応答を取り込むまで処理枠を保持する。素材、文字起こし、字幕、区間入力は二つの代表値に縮める。クリップとその変更履歴は、空、手動、AI の三つで表す。素材の差し替えは空の編集状態を開く操作として扱う。TLC の探索対象はこのモデルの到達状態。

## 実行

Node.js、npm、Java を用意する。Quint と npm の依存関係はロックファイルで固定する。初回は依存関係と TLC の取得にネットワーク接続を使う。

```sh
cd verification/quint
npm ci --ignore-scripts
npm run check
```

CI も同じ手順でシナリオテスト、TLC による全探索、ITF フィクスチャの再生成チェックを実行する。 [Quint の CI](../../.github/workflows/formal-quint.yml)

## 作業履歴の Undo / Redo

モデルでは編集済みのスナップショットの列と現在位置で履歴を表す。Rust 実装は Undo と Redo の二つのスタックを使う。操作と結果を ITF に記録し、Rust の受入テストで実際に同じ操作を行って照合する。 [Quint モデル](EditHistory.qnt) · [Rust 実装](../../rust/src/history.rs) · [受入テスト](../../rust/tests/history_acceptance.rs)

| 操作 | 条件 | 遷移と結果 |
| --- | --- | --- |
| 字幕・クリップ区間の編集 | 有効で値が変わる | 通常の Redo 候補を破棄し、新しい状態を追加する |
| 字幕・クリップ区間の編集 | 同じ値 | 履歴も編集内容も保持し、変更なしを返す |
| クリップ区間の編集 | 無効な区間 | 履歴も編集内容も保持し、エラーを返す |
| Undo / Redo | 対応する候補がある | スナップショット列を保持し、現在位置を前後に一つ動かす |
| Undo / Redo | 対応する候補がない | 履歴も編集内容も保持し、変更なしを返す |
| 保存 | 正常に保存できる | スナップショット列と現在位置を保存し、編集中の状態を保持する |
| 再読込 | 保存済みのプロジェクトがある | 保存した列と現在位置を復元する。以後の再読込にも同じ保存内容を使う |

通常の Redo 候補を破棄する振る舞いを Quint と ITF で確認する。候補から外れた変更を作業履歴に表示するシナリオは BDD で計画中。 [通常の Redo に関する BDD](../../docs/features/edit-history.feature#L47) · [作業履歴の表示に関する BDD](../../docs/features/edit-history.feature#L53)

TLC は字幕1件、字幕と区間それぞれ2種類の有効値、無効区間1種類、最大4スナップショット、保存先1つの有限モデルを全探索する。保存・再読込は正常に完了し、履歴が保存上限に収まる経路を扱う。履歴の切り詰めと不正なアーカイブは Rust の受入テストで確認する。ファイル操作そのものが失敗する経路はモデルの範囲外。

Rust で ITF を3本再生し、編集内容、操作結果、Undo / Redo の可否を各ステップで照合する。保存のトレースでは、字幕と区間を編集して区間だけ Undo し、保存する。その後の字幕編集で Redo 候補を消してから開き直し、保存時の字幕と区間、Undo と Redo の可否、Redo で区間が戻り、続けて2回 Undo すると元の字幕と区間に戻ることを照合する。保存・再読込の操作結果は編集対象を返さないため、ITF では `unchanged` と表す。再読込後の編集内容と履歴は別途照合する。 [保存・再読込の ITF](traces/edit_history_reopen.itf.json)

Rust の BDD と Proptest でも保存・再読込を確認する。Proptest は同じ生成操作列から2つのプロジェクトを作り、片方を保存して開き直す。その後の操作と Undo / Redo が、保存せずに続けたもう片方と一致することを確認する。 [保存・再読込の BDD](../../docs/features/edit-history.feature#L59)

`verification/quint` でモデルを実行して ITF を更新する。

```sh
npm run check:history-trace -- --write
```

リポジトリルートで、通常の Rust ビルド環境から再生テストと Proptest を実行する。

```sh
cargo test --manifest-path rust/Cargo.toml --locked --test history_acceptance
```
